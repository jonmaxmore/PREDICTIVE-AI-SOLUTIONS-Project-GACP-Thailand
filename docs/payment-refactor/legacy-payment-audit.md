# Legacy Payment Audit — Two-Step → Single Lump-Sum Checkout with Split-Invoicing

- **Date:** 2026-08-02
- **Scope:** every artifact that encodes the two-step payment model (Phase 1 document fee + Phase 2 assessment fee) across Prisma schemas, backend services, HTTP surface, the workflow SSOT, the web frontend, the Flutter app, and fee/accounting config.
- **Method:** seven parallel territory sweeps with grep-evidenced verdicts, followed by an adversarial verification pass in which every DELETE claim was handed to an independent agent instructed to refute it by finding a live caller. 62 DELETE claims → 55 confirmed, 7 refuted and downgraded. 266 artifacts inventoried in total.
- **Status:** AUDIT ONLY — no production code was modified. This document is the input to the Step-2 data-model redesign.

## Target model (restated)

One checkout per application: a single PromptPay QR / card charge for `total_payable_amount`, itemized as `dtam_fee_amount` (pass-through, VAT-exempt) + `platform_fee_net` + `platform_fee_vat` (7%) = `platform_fee_gross`. Two documents generated per settlement: a **tax invoice/receipt** for the platform fee (company revenue) and a **pass-through disbursal receipt** for the DTAM government fee (VAT-exempt). A `dtam_remittance_status` lifecycle (`PENDING → BATCHED → REMITTED → RECONCILED`) tracks the pass-through liability from applicant payment to government remittance.

## The two-step model as it exists today (one paragraph)

On submit, quotation-service issues per-issuer quotations; accepting them (or the wizard auto-chain) mints **two invoices per phase** — a STATE component (DTAM fee, `vat=0`) and a PLATFORM component (service fee + 7% VAT) — so a fully-paid application carries **four invoices, four slips, four receipts**. The applicant sees a "transfer twice" screen per phase, uploads one PromptPay slip per invoice against per-side bank accounts, and side-walled accountants (`ACCOUNT_DTAM` / `ACCOUNT_PLATFORM`) approve each slip. `computePhaseSettlement` declares a phase paid only when *both* sibling invoices settle, which drives six workflow states (`PENDING_DOC_FEE → PHASE_1_SLIP_UNDER_REVIEW → DOC_FEE_PAID` and the Phase-2 mirror), nine transition edges, and every downstream projection (tracking ladder, dashboards, notifications, scheduler gates, Prometheus buckets).

## Key findings

1. **The target fee decomposition already exists.** `modules/billing`'s internal fee-service computes exactly `stateTotal / platformTotal / vatTotal / grandTotal` = `dtam_fee / platform_fee_net / platform_fee_vat / total_payable`. The redesign consumes the whole-application result instead of the per-phase slices — the math itself does not change.
2. **The target accounting doctrine already exists, dormant.** `journal-entry-service` contains a complete collection-agent model — `buildPaymentEntryLines`' components path (Dr Cash / Cr Payable-to-DTAM / Cr Revenue / Cr Output-VAT) and `buildRemittanceEntryLines` / `recordRemittanceToDtam` for the clearing entry — currently with **zero production callers**. It should be revived, not rebuilt. The live "two transfers, never combined" doctrine (the `recordPaymentEntry` STATE short-circuit) is what retires.
3. **`dtam_remittance_status` needs net-new schema.** There is no existing persistence for the remittance lifecycle. The orphan `PaymentReconciliation` model is *not* a usable base (Float money columns, never written); `bank-reconciliation-service` is the right chassis for the `RECONCILED` leg only.
4. **The PSP callback is a green-field build.** No payment-gateway webhook route is mounted at all — `payment-webhook-service.js` is an unmounted OMISE/2C2P-era remnant, and the gateway lineage (`payment-service-webhook-flow`, `payment-legacy-service`) is runtime-dead. The single-charge confirmation path can be designed clean.
5. **The state swap is mechanically forced.** Three boot-time totality assertions, the verbatim contract test suite, and the `no-legacy-status-vocabulary` ESLint ratchet mean collapsing the two payment gates into one cannot ship half-done — every projection (status-machine API, tracking ladder, dashboard stages, Flutter mirrors) breaks loudly until updated. This machinery is KEEP; the migration rides on it.
6. **Per-issuer receipt numbering and dual-key RSA signing survive intact** — they become the engine of the split-document generation (platform tax invoice + DTAM disbursal receipt).
7. **A live frontend defect surfaced in passing:** `invoice-detail-modal` PATCHes a nonexistent `/invoices/:id` (cancel/void 404s today). Refunds/debit-notes are fully built server-side with zero frontend callers.
8. **The Flutter app has no invoice/receipt viewer at all** — the split-document surface on mobile is net-new UI, not a refactor.

## Deprecation plan (ordered, expand-migrate-contract)

**Wave 0 — dead-code purge (can ship NOW, independent of the redesign).** Remove the 55 adversarially-confirmed DELETE items: the runtime-dead gateway lineage, the entire unmounted `/api/quotes` router and its handlers, dead pricing/receipt/forfeit/split-calculator routes, two zero-importer Flutter payment stacks, dead web components (`quote-step.deprecated`, `receipt-document`, `RevenueSummaryCards`, …), orphan Prisma models with zero production reads (`PaymentAudit`, `PaymentReconciliation`, `IssuerBankAccount`), and dead service exports (`processPayment` / `finalizeSubmission`). Nothing in this wave changes behaviour; each removal cites its verification evidence.

**Wave 1 — schema EXPAND.** Add the new shapes alongside the old: the checkout/charge record (reviving `PaymentTransaction`'s satang-Int + `idempotencyKey` + webhook columns, phase column deprecated), itemized breakdown rows on `InvoiceLineItem` (new codes, `isTaxable` flags; `phase` column deprecated), the net-new `dtam_remittance` model (`PENDING/BATCHED/REMITTED/RECONCILED`), and the two-document generation columns. No old column dropped; both models coexist.

**Wave 2 — single checkout + split documents.** New checkout endpoint mints ONE invoice with the itemized breakdown, single QR payload, PSP confirmation path (green-field webhook with signature verification), revived collection-agent journal entries, split-document generation on settlement (platform tax invoice via the existing per-issuer numbering + RSA signing; DTAM disbursal receipt), `dtam_remittance` rows opened per settlement. Feature-flagged; the two-step path still works.

**Wave 3 — workflow state collapse.** The two 3-state payment gates become one (`PENDING_PAYMENT → [SLIP_UNDER_REVIEW?] → PAYMENT_SETTLED`, exact vocabulary per D1/D2), driven through `application-status-writer`, both boot assertions, the contract suite, and the ESLint ratchet; every projection (tracking ladder, dashboards, action cards, notifications, scheduler gates, Flutter/web mirrors, i18n copy) updates in the same change because the totality gates force it. Mid-flight rows handled per D2.

**Wave 4 — CONTRACT.** After production confirms zero consumers: drop `Application.phase1*/phase2*` (14 columns), `Invoice.items` JSON, the `PHASE_{1,2}_{STATE,PLATFORM}_FEE` serviceType vocabulary and its classifiers, `computePhaseSettlement` and the per-side slip wall (re-purposed per D1), and the retired workflow states. Two deployments, same discipline as the role canonicalization.

### Backend payment services under apps/backend/services (payment/invoice/receipt/slip/fee/quote/note/refund modules)

The two-step model in services/ runs: quotation-service issues per-issuer (DTAM+PLATFORM) quotations on submit; quotation accept and wizard submit mint TWO invoices per phase via application-phase-invoice-methods.ensurePhaseInvoices (STATE vat=0, PLATFORM +7% VAT, GAP-5 frozen-quote pricing); payment-service-phase-flow.createPhase1Payment creates the PENDING PaymentTransaction and PENDING_DOC_FEE state (Phase 2's twin is already route-dead, replaced by the DOC_APPROVED auto-chain); payment-slip-service owns the canonical PENDING→PAID transition with a per-side (ACCOUNT_DTAM/ACCOUNT_PLATFORM) SoD wall, quotation/consent gates, and a FOR-UPDATE write-skew guard that exists only because a phase settles across two sibling invoices; on approve, invoice-service auto-issues a per-issuer-numbered receipt which receipt-auto-sign-service signs with the matching legal entity's RSA key. phase-billing-service.computePhaseSettlement (phasePaid = statePaid && platformPaid) is the most widely shared encoding of the split and is consumed by seven-plus modules including the scheduler gate. The gateway-webhook lineage (payment-service-webhook-flow, payment-legacy-service, verifyWebhookSignature in two copies) is confirmed dead at runtime — tests only — and application-payment-finalization-methods' processPayment/finalizeSubmission have zero callers of any kind. The pieces the target model needs already exist in embryo: the itemized fee quantities (modules/billing stateAmount/platformAmount/vatAmount/phaseTotal), the charged-total-authoritative breakdown (payments/phase-breakdown), per-issuer receipt numbering and dual-key signing, the canonical STATE/PLATFORM side classifier, and the PAYABLE_TO_DTAM liability + recordRemittanceToDtam clearing entry in journal-entry-service (adjacent territory) that the dtam_remittance_status machine would formalize; the main demolition is everything keyed on invoice.serviceType as a side discriminator and everything that assumes one phase = two invoices = two slips = two receipts.

### HTTP surface — apps/backend/routes/api/finance/**, payment/invoice/slip/receipt/quote/checkout routes elsewhere under routes/, webhook handlers, payment-adjacent controllers, with caller evidence from apps/web-app and apps/mobile-app

The two-step HTTP surface is cleanly layered: initiation (POST /payments/create + /payments/phase1 minting per-phase STATE+PLATFORM invoice pairs; /payments/phase2 already a 410 tombstone), collection (GET /payments/bank-accounts/active?phase&side + GET /finance/issuers/by-service-type feeding two payment cards, POST /payments/slip/upload per invoice), review (side-walled /payments/slip pending/approve/reject driving PHASE_x_SLIP_UNDER_REVIEW → *_FEE_PAID), and documents/reporting (/invoices receipts + PDFs keyed to the serviceType side taxonomy via invoice-helpers). There are NO payment-gateway webhook routes at all — payment-webhook-service.js is an unmounted OMISE/2C2P-era remnant, so the checkout redesign's PSP callback is a green-field build. A large legacy stratum is already caller-dead and can be deleted independent of the redesign: the entire /api/quotes router, /pricing/invoice/:phase, /config/pricing*, receipts issued/failures/retry, forfeit, split-calculator, by-issuer-type, GET /payments, POST /prepare-preview, plus two unrouted Flutter payment stacks calling phantom endpoints (/v2/payments/confirm, /payments/checkout). ### apps/web-app (web frontend): payment pages, components, hooks, API clients, state maps

The web-app frontend encodes the two-step model in three concentric rings. The core is the applicant payments hub (/health/payments) plus the components/payments family and payment-service.ts: invoices are classified into PHASE_1/PHASE_2 x STATE/PLATFORM (with an amount<=5000 fallback heuristic), rendered as a two-card 'transfer twice' section per phase, each card fetching its own issuer/bank/PromptPay QR, and each settled by a per-side slip upload reviewed in the provider accounting dashboard's side-walled slip queue — a single-QR itemized checkout replaces TwoCardPaymentSection outright and collapses PaymentInvoiceCard, the slip modal's (phase, side) bank resolution, and the per-issuerType quotation accept into one payee/one acceptance. The second ring is state plumbing: workflow-states.ts, status-mapping.ts, health-dashboard-stage.ts, submission-claim.ts, resolvePaymentFacts and ~29 files of state literals all hard-code the PENDING_FEE -> SLIP_UNDER_REVIEW -> FEE_PAID triples and must be re-pointed in lock-step with the backend. The third ring is copy and pricing math (fees.ts totals, marketing/terms/onboarding/FAQ, four i18n dictionary families) that publicly explains the two-transfer legal rationale. Confirmed dead by grep regardless of the redesign: quote-step.deprecated.tsx, receipt-document.tsx, renewal success-step.tsx, RevenueSummaryCards, DocumentLink, use-master-data.ts, the whole types/database* mirror, and the useInvoice/calculateFeeContract exports in use-pricing.ts. The genuinely open product decisions are (a) whether manual slips survive at all under the lump-sum QR (deciding the fate of both slip modals and SlipHistorySection, and forcing a new settlement path for subscriptions which piggyback on the slip pipeline) and (b) whether the unwired renewal payment screens are rebuilt on the new checkout or removed.

### fee math + accounting config (fee calculation services, VAT handling, DTAM_*/PLATFORM_* env config, computePhaseSettlement + settlement helpers, accounting-route side-scoping, reconciliation/remittance machinery)

The fee math itself is in good shape for the refactor: modules/billing/internal/fee-service.js already computes the exact target decomposition (stateAmount/platformAmount/vatAmount per scope, plus whole-application stateTotal/platformTotal/vatTotal/grandTotal = dtam_fee/platform_fee_net/platform_fee_vat/total_payable), and config/business-rules.js is the single overridable rate source — the real work is killing the duplicate flat table in config/payment-fees.js (mostly dead helpers) and collapsing per-phase consumers onto the whole-application result. The main structural conflict is computePhaseSettlement (phase-billing-service.js), which defines "paid" as STATE-invoice AND PLATFORM-invoice both settled per phase and is read by ~15 workflow/dashboard callers; every side-scoping mechanism (finance/invoice-side.js, invoice-helpers.js invoiceSideWhere, accounting.js dashboards, bank-reconciliation bookSide) classifies at the Invoice.serviceType level and breaks for a combined checkout invoice. Critically, the repo contains BOTH accounting doctrines: the live B16-C "two transfers, never combined" model (recordPaymentEntry STATE short-circuit, 2151-001 marked legacy) and a dormant collection-agent model — buildPaymentEntryLines' components path (Dr Cash / Cr Payable-to-DTAM / Cr Revenue / Cr VAT) and buildRemittanceEntryLines/recordRemittanceToDtam (currently zero production callers) — that is almost exactly the target model and should be revived rather than rebuilt. There is NO existing persistence for the dtam_remittance_status lifecycle (no model, column, or enum; only the aggregate GL remittance entry builder), so PENDING/BATCHED/REMITTED/RECONCILED needs new schema, with bank-reconciliation-service as the chassis for the RECONCILED leg. Issuer/bank identity config (invoice-issuers.js, DTAM_*/PLATFORM_* envs) survives largely intact for split-document generation, but PLATFORM_BANK_ACCOUNT is still PENDING_FINANCE_CONFIRMATION — launch-blocking once it becomes the sole receiving account — and the ACCOUNT_DTAM/ACCOUNT_PLATFORM SoD role split survives with the DTAM side re-purposed from slip review to remittance oversight.
