# ADR 0004: โมเดลบัญชี 3 ฝั่ง ตามระเบียบหมอพร้อม (Health ID · Provider ID) และ ThaID

สถานะ: ยอมรับ · operator อนุมัติ spec 2026-09-09 ("อนุมัติ") · ทำเสร็จใน branch feat/account-model 2026-09-09 · ผู้ตัดสิน: operator

## บริบท

operator สั่งให้ยึดระเบียบหมอพร้อม/กระทรวงสาธารณสุข "เป๊ะ" เป็นแกนของบัญชีผู้ใช้ และใช้ ThaID ตามตัวอย่าง Relying Party ของ ETDA ระบบเดิม (M0) มี `IdentityProvider.MORPHROM` ค่าเดียวและบทบาท 7 แบบที่ปนคนของกรมกับคนของบริษัท (`FINANCE_OFFICER`, `SYSTEM_ADMIN`) จึงบอกไม่ได้ว่าใครเป็นเจ้าหน้าที่ของใคร

## การตัดสิน

1. บุคคลหนึ่งคน = `User` หนึ่งแถว มีตัวตนได้หลายทาง (`THAID`, `MORPHROM_HEALTH_ID`, `DEV_LOCAL`) เชื่อมด้วย HMAC ของเลขบัตร
2. สามฝั่ง (`RoleSide`): ผู้รับบริการ (`APPLICANT`) · เจ้าหน้าที่กรม (`CERTIFICATION_BODY` เข้าด้วย Health ID + ตรวจ Provider ID + สังกัดที่อนุญาต) · บริษัทผู้ให้บริการแพลตฟอร์ม (`PLATFORM_OPERATOR` เข้าด้วย ThaID + รายชื่อพนักงานที่บริษัทอนุญาต) ทางเข้าและหน้าจอแยกกัน
3. บทบาท 9 แบบ แต่ละองค์กรมี "การเงิน" และ "ผู้ดูแลระบบ" ของตัวเอง ไม่มี super admin สิทธิ์ดูแลเซิร์ฟเวอร์ไม่ใช่บทบาทในแอป
4. บทบาทมีผล = บทบาทที่ถูกมอบ ∩ บทบาทที่เครดิตของฝั่งอนุญาต คำนวณใหม่ทุกครั้งที่ล็อกอิน
5. ไม่มีรหัสผ่านที่ระบบเก็บเอง local login เฉพาะ development (ตาม ADR 0001 ข้อ 5)

รายละเอียดทั้งหมดอยู่ใน [spec 2026-09-09](../superpowers/specs/2026-09-09-account-model-design.md)

## ผลที่ตามมา

- ADR 0001 ข้อ 5 ขยายเป็น "ผู้รับบริการ = Health ID หรือ ThaID · เจ้าหน้าที่กรม = Provider ID · บริษัท = ThaID + รายชื่อ" และข้อ 13 เปลี่ยน `FINANCE_OFFICER` เป็น `PLATFORM_OPERATOR_FINANCE_OFFICER`
- glossary §2 เป็น 9 บทบาท · ชื่อ `FINANCE_OFFICER` และ `SYSTEM_ADMIN` เข้ารายการคำต้องห้าม
- ต้องได้ client จาก 2 หน่วยงานก่อนขึ้น demo จริง: สำนักสุขภาพดิจิทัล (Health ID + Provider ID) และกรมการปกครอง (ThaID) ระหว่างนั้นใช้ dev login และ fake client ในการทดสอบ
- การกระทบยอดกรม–บริษัทเข้าขอบเขต M4 (บันทึกงวดนำส่ง + ยืนยันรับ)
