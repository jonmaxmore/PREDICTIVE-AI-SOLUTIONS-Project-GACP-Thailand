## 1. โมเดลที่ใช้จริง (W14 — คำสั่ง operator 2026-08-22)

**ผู้ออกเอกสารมีรายเดียว: บริษัท** เกษตรกรซื้อ *บริการ* จากบริษัท จ่ายให้บริษัท
บริษัทไปเคลียร์กับกรมฯ **นอกระบบนี้**

```
ค่าบริการ = ราคาเต็ม + ค่าแพลตฟอร์ม 10% ของราคาเต็ม
ยอดชำระ  = ค่าบริการ + VAT 7% ของค่าบริการทั้งก้อน
```

**ไม่มีการยกเว้นภาษีส่วนใด เก็บ VAT เต็มทั้งก้อน** (operator 2026-09-05)

### การลงบัญชี — บริษัทเป็น principal

operator 2026-09-05: *"เรื่องรับเงิน บริษัทรับแทนเป็นรายได้ทั้งหมด เพราะเรื่องจ่ายเงิน
บริษัทเป็นผู้จ่ายกรม ภายหลัง"*

**operator 2026-09-29: บริษัทชำระกับกรมฯ นอกระบบ และลงบัญชีในสมุดบัญชีของบริษัทเอง** —
แพลตฟอร์มไม่มีเจ้าหนี้กรมฯ ไม่มี pipeline นำส่ง ไม่แยกส่วนค่าธรรมเนียมของกรมฯ

ตอนรับเงิน (งวดที่ 1 · 1 รูปแบบ) — สามบรรทัด ไม่มีบรรทัดของกรมฯ:

```
Dr 1110-001 เงินสด/ธนาคาร              5,885
  Cr 4110-001 รายได้ค่าบริการ            5,500   ← ทั้งก้อน ไม่ใช่เฉพาะ 10%
  Cr 2131-001 ภาษีขายตั้งพัก               385
```

ประวัติ (2026-09-05 → 2026-09-29): รายการเดียวกันเคยมีคู่ `Dr 5110-001 ค่าธรรมเนียมกรมฯ (ต้นทุน) /
Cr 2151-001 เจ้าหนี้ กรมการแพทย์แผนไทยฯ` ต่อท้าย — ถอดพร้อมสองบัญชีนั้นตามมติ 2026-09-29
(สาขา chore/remove-dtam-accounting-layer · เทสกัน `dtam-accounting-layer-removed.test.js`)

ตอนนำส่งกรมฯ (เดิมคือชุดรายเดือน · `dtam-remittance-service.js` — **ถอดแล้ว 2026-09-29** ตามคำสั่ง operator 2026-09-11 "ถอดออกทั้งระบบ" · บริษัทนำส่งนอกระบบนี้ · การลงบัญชีด้านล่างเป็นประวัติ):

```
Dr 2151-001 เจ้าหนี้ กรมการแพทย์แผนไทยฯ  ยอดรวมชุด
  Cr 1110-001 เงินสด/ธนาคาร               ยอดรวมชุด
```

**เดิมลงว่า** Cr เจ้าหนี้กรมฯ 5,000 / Cr รายได้ 500 — คือรายได้ 500 บาทบนยอดขาย 5,885
ไม่มีต้นทุนขาย และถือว่าเงิน 5,000 เป็นของคนอื่นตั้งแต่วินาทีที่รับเข้ามา ทั้งที่เก็บ VAT บนมัน
กำไรขั้นต้นเท่าเดิม (500) แต่ยอดขาย ต้นทุน และเหตุผลที่หนี้เกิด ตรงกับความจริงแล้ว

| | ต่อ 1 รูปแบบการปลูก |
|---|---|
| งวดที่ 1 (ตรวจเอกสาร) | 5,000 + 500 + 385 = **5,885** |
| งวดที่ 2 (ตรวจพื้นที่) | 25,000 + 2,500 + 1,925 = **29,425** |
| **รวมคำขอใหม่** | **35,310** |
| ต่ออายุ (เก็บครั้งเดียว) | 30,000 + 3,000 + 2,310 = **35,310** |

คูณตามจำนวนรูปแบบการปลูก: 1 / 2 / 3 รูปแบบ = 35,310 / 70,620 / 105,930

**ที่นิยามอยู่ที่เดียว**: `apps/backend/config/business-rules.js` → `FEE_DEFAULTS`
บังคับด้วย probe `fee-single-source` และ ratchet `dup-source`

## 2. สิ่งที่ **ไม่ใช่** โมเดลนี้ — และยังมีร่องรอยอยู่ในโค้ด

โค้ดวันนี้มีสามโมเดลซ้อนกันอยู่ นี่คือต้นเหตุความเข้าใจผิดที่ operator สั่งให้เคลียร์

| | โมเดล | ยกเลิกเมื่อ | ร่องรอยที่ยังเหลือ |
|---|---|---|---|
| **A** | **สองกระแสเงิน** — ผู้ยื่นโอนค่าธรรมเนียมรัฐตรงไปกรมบัญชีกลาง เงินไม่ผ่านบัญชีบริษัท | 2026-08-22 (W14) | `STATE_FEE_NOT_IN_PLATFORM_BOOKS` short-circuit · `PHASE_1/2_STATE_FEE` → `DTAM_RECEIPT` ใน document-numbering · `bookSide` DTAM/PLATFORM **99 จุด** ใน 7 ไฟล์ · role `ACCOUNT_DTAM` / `ACCOUNT_PLATFORM` |
| **B** | **ตัวแทนรับชำระ** — บริษัทเก็บแทนกรมฯ ตั้งเป็นหนี้ 2151-001 แล้วนำส่งรายเดือน | 2026-08-22 (W14) | คอลัมน์ `dtam_fee_amount` · `dtam_remittance_status` · ตาราง `dtam_remittance_batches` · บัญชี 2151-001 (`journal-entry-service.js:154` ระบุเอง "legacy … Do NOT add new credits") · **และ `services/checkout/dtam-remittance-service.js` ที่เพิ่งสร้างวันนี้ตาม GOALS.md G1 ข้อ 4** |
| **C** | **ผู้ออกรายเดียว (ที่ใช้จริง)** | — | คือข้อ 1 ข้างบน |

> **ข้อสังเกตที่ต้องพูดตรง ๆ**: GOALS.md G1 ข้อ 4 ("remittance pipeline") เขียนไว้ก่อน W14
> และไม่เคยถูกแก้ตามคำสั่งนั้น งานที่ทำเสร็จวันนี้จึงไปต่อโมเดล B ที่ถูกยกเลิกแล้ว —
> โค้ดถูกต้องตาม schema ปัจจุบัน แต่ schema ปัจจุบันเป็นของโมเดลที่ไม่ใช้แล้ว

## 3. คำเรียกที่ผิดและควรเปลี่ยน

หลักของ operator: *"ตั้งชื่อให้ถูก อย่าเก็บชื่อเก่าไว้ · เปลี่ยนชื่อที่ผิด แทนที่จะซ่อนค่าที่ถูกไว้หลังชื่อที่ผิด"*

| ชื่อวันนี้ | เป็นจริง ๆ คือ | หมายเหตุ |
|---|---|---|
| `dtamFeeAmount` (คอลัมน์ `dtam_fee_amount`) | **ราคาเต็ม** — ส่วนหนึ่งของค่าบริการของบริษัทเอง ไม่ใช่เงินของกรมฯ | ค่าถูก ชื่อผิด · เปลี่ยนชื่อต้องมี migration |
| `platformFeeNet / Vat / Gross` | ค่าแพลตฟอร์ม 10% และ VAT | VAT จริง ๆ คิดบนค่าบริการทั้งก้อน ไม่ใช่บนส่วนแพลตฟอร์ม — ชื่อชวนให้เข้าใจสูตรเก่า |
| `PAYABLE_TO_DTAM` (2151-001) | หนี้ที่ไม่ได้เกิดจากรางจ่ายเงินปัจจุบัน | ไฟล์ระบุเองว่า legacy |
| `ACCOUNT_DTAM` / `ACCOUNT_PLATFORM` | บทบาทบัญชีสองฝั่ง ของโมเดลที่มีสองกระแสเงิน | โมเดลปัจจุบันมีกระแสเดียว |

## 5. คำตัดสินของ operator (2026-09-05) และสิ่งที่ทำตามแล้ว

**D2 — "ผูกกับคำขอ — เก็บไว้ แต่เปลี่ยนชื่อ"** — *superseded 2026-09-29: operator ตัดสินให้ชำระกับกรมฯ
นอกระบบ ลงบัญชีในสมุดบัญชีบริษัทเอง ⇒ 2151-001, การลงบัญชีของมัน และ `dtamPayableAmount` ในฐานะ

**ถูกต้องและจำเป็น** ไม่ใช่ซากของโมเดล B · ตรวจซ้ำแล้วห่วงโซ่ครบ: settlement เครดิต

เลิกเรียก 2151-001 ว่า legacy · แก้ memo จาก "Collected on behalf of DTAM" เป็น

**D3 — "ให้บัญชีบริษัทกับกรมฯ กระทบยอดกันได้ · dtam ดูตัวเลขได้เหมือนบริษัท แต่ไม่เห็นค่าบริการ

## 6. แฟล็กสองหน้าที่ — บทเรียนที่ควรจำ

`STRIPE_CHECKOUT_ENABLED` เคยตัดสินสองเรื่องที่ไม่เกี่ยวกัน: **เกตเวย์พร้อมใช้ไหม** (เรื่องของ
environment โดยชอบ) และ **บริษัทรับรู้รายได้อย่างไร** (ไม่ใช่เรื่องของ environment เลย)
ผลคือ environment ที่ไม่ได้ตั้งแฟล็ก — ซึ่งเป็นค่าเริ่มต้น — เปลี่ยนโมเดลบัญชีเงียบ ๆ

ประตู checkout ยังตอบ 503 เมื่อไม่มี Stripe เหมือนเดิม และควรเป็นแบบนั้น
แต่การลงบัญชีไม่ขึ้นกับ environment อีกต่อไป
