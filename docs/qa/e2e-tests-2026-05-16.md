# E2E Test Suite — Iter 23 (2026-05-16)

Status: bootstrapped — 1 spec, API-mocked.

## Layout

The project now has **two parallel Playwright suites**, both registered in
`apps/web-app/playwright.config.ts`:

| Folder | Purpose | Backend | CI cost |
|--------|---------|---------|---------|
| `apps/web-app/e2e/` | Legacy. Live backend, real Docker stack, full lifecycle. | Real | High (docker-compose up + seed) |
| `apps/web-app/playwright/` | **New (Iter 23)**. API-mocked, no Docker. | Fully mocked via `page.route()` | Low (frontend + node) |

Going forward, new specs should default to `playwright/` unless they
specifically exercise backend code paths.

## How to run locally

```bash
cd apps/web-app

# Single spec, single browser, headed (visible browser):
npx playwright test playwright/farmer-payment-flow.spec.ts --project=chromium --headed

# All projects (chromium + firefox + webkit + mobile), headless:
npx playwright test playwright/farmer-payment-flow.spec.ts

# Just list tests without running:
npx playwright test playwright/ --list

# Open HTML report after a run:
npx playwright show-report
```

The new suite **does not require Docker** — start `npm run dev` (port 3000)
in one terminal and run the test in another. The legacy `e2e/` suite
still requires the full backend stack on `E2E_BASE_URL`.

### Environment variables

| Var | Default | Use |
|-----|---------|-----|
| `E2E_BASE_URL` | `http://localhost` | Where the tests point. Set to `http://localhost:3000` for `npm run dev` workflow. |
| `E2E_IGNORE_HTTPS_ERRORS` | `false` | Set `true` when hitting a self-signed staging cert. |

The Iter-23 suite ignores `E2E_TEST_IDENTIFIER` / `E2E_TEST_PASSWORD` —
it seeds auth via localStorage + fake JWT (see `playwright/fixtures.ts`).

## Test fixtures

`apps/web-app/playwright/fixtures.ts` exposes:

- `loginAsHealthUser(page, overrides?)` — seeds `auth_token` and
  `auth_user` in localStorage via `page.addInitScript()` so the
  /health/** layout treats the user as authenticated. Returns the
  fixture user so the test can reference IDs.
- `loginAsAccountDtam(page, overrides?)` — same shape with the
  ACCOUNT_DTAM role for the approval side of the flow.
- `mockApi(page, { route, method, status, body })` — generic
  `page.route()` wrapper that JSON-serialises a payload. Multiple calls
  layer (last-write-wins for overlapping routes).

The fake JWT uses base64url-encoded header/payload + a stub signature.
This is safe because the frontend `AuthService` decodes the payload but
delegates signature verification to the backend (which the mock
intercepts). The token has a 1-hour expiry stamp.

## Test data setup

Iter 23 uses **inline mock fixtures** — no Postgres or Redis required.
The test file declares:

- `buildInvoicePayload({ stateIsPaid?, platformIsPaid? })` — generates
  the `/api/invoices/my` payload for either pre- or post-approval state.
- `ISSUER_STATE`, `ISSUER_PLATFORM` — frozen issuer detail blobs
  matching the shape of `apps/backend/config/invoice-issuers.js`.
- `BANK_ACTIVE_STATE` — frozen bank account for slip-modal display.

Trade-off: the inline data ages alongside the type contracts. If
`payment-service.ts` adds a required field, the test fixture needs an
update too. Acceptable for Iter 23 (one spec); revisit if the suite
grows past ~5 specs.

## Selectors used

Stable selector strategy, in order of preference:

1. `data-testid` — used for the two-card container and per-card
   identification:
   - `two-card-phase-งวดที่ 1`
   - `payment-invoice-card-STATE`
   - `payment-invoice-card-PLATFORM`
2. `getByRole({ name })` — buttons (อัปโหลดสลิป, ปิดหน้าต่าง, รีเฟรช,
   ส่งสลิปให้ตรวจสอบ) and headings.
3. `getByText` / `getByPlaceholder` — Thai strings that are unlikely to
   change without a UX review (numeric amounts, the ทำไมต้องโอน 2 ครั้ง
   footnote, the TRX placeholder).

No additional `data-testid` attributes were needed — the existing ones
on `PaymentInvoiceCard` and `TwoCardPaymentSection` (added in B18-B)
proved sufficient.

## Known limitations of Iter 23

- **No real wizard run.** The happy-path test does navigate to
  `/health/applications/new` and asserts the redirect to
  `/new/step/1`, but does NOT fill the 11-step wizard form. The
  payments page receives mocked invoices instead of invoices generated
  by a wizard run. Justification: the wizard's steps are tested
  individually in Jest, and end-to-end wizard coverage already exists
  in `e2e/e2e-golden-scenario.spec.ts` (live-backend suite).
- **Approval is mocked, not real.** Post-upload, we re-route
  `/api/invoices/my` to return the STATE invoice as paid rather than
  invoking the real `POST /api/payments/slip/:id/approve`. The
  finance-reviewer side of the flow needs its own spec — proposed for
  Iter 24.
- **No PDF download verification.** The "ดาวน์โหลด PDF" button is
  visible but not clicked. Playwright can capture downloads, but
  asserting on PDF content is overkill for the smoke pass.
- **No mobile viewport pass yet.** Config lists Mobile Chrome / Mobile
  Safari projects but the new spec is only validated on `chromium`.
  Cross-browser run is on the CI roadmap.

## CI integration plan (not yet committed)

Proposed `.github/workflows/e2e-mocked.yml` (DO NOT commit from this
iter — orchestrator decides timing):

```yaml
name: E2E (API-mocked)

on:
  pull_request:
    paths:
      - 'apps/web-app/**'
  push:
    branches: [main]

jobs:
  playwright:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: apps/web-app/package-lock.json
      - run: npm ci
        working-directory: apps/web-app
      - run: npx playwright install --with-deps chromium
        working-directory: apps/web-app
      - name: Start Next.js dev server
        run: npm run dev &
        working-directory: apps/web-app
        env:
          NODE_ENV: development
      - name: Wait for server
        run: npx wait-on http://localhost:3000 --timeout 60000
      - name: Run Playwright tests
        run: npx playwright test playwright/ --project=chromium
        working-directory: apps/web-app
        env:
          E2E_BASE_URL: http://localhost:3000
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: apps/web-app/playwright-report/
          retention-days: 7
```

Targets ~3 min wall-clock once cached. The legacy `e2e/` suite stays in
its own workflow file (already exists) since it needs docker-compose.

- `mockGeolocation(page, { lat, lng, accuracy?, origin? })` —
  geolocation override for the auditor field-app GPS check-in. Uses
  **two layers** for resilience:
   1. **Native path (preferred):** `context.setGeolocation()` +
      `context.grantPermissions(['geolocation'])`. This is the
      Playwright-recommended approach and works across Chromium,
      Firefox, and Webkit without monkey-patching.
   2. **JS shim fallback:** `page.addInitScript()` that redefines
      `navigator.geolocation.getCurrentPosition` /
      `.watchPosition` to immediately resolve with the same
      coordinates. Belt-and-braces for any page that polls
      `navigator.geolocation` before the native event has wired up
      (e.g., capacitor-style mobile shells).

### Selectors used (auditor flow)

Same preference order as Iter 23:

1. **`data-testid`** — preferred where present in B25-C frontend:
   - `scheduler-queue-row-{appId}`
   - `scheduler-date` / `scheduler-time` / `scheduler-auditor`

2. **`getByRole({ name })`** — buttons (จัดตาราง, เริ่มตรวจ, ส่งผลการตรวจ),

   churn during the iteration.

Both specs use the `.or()` resilience pattern: any test step that
depends on a B25-C selector tries the `data-testid` first, then falls
back to role+name, then to Thai text. This keeps the spec discovery
green even if B25-C's `data-testid` set drifts during integration.
No new `data-testid` attributes were added by Iter 25 (max-5 budget
from the boundary spec was not needed).

### Known limitations of Iter 25

- **Frontend B25-C is parallel work in this iter.** The new spec
  targets routes (`/provider/scheduler/queue` and
  `/provider/audits/:id/inspect`) that may not yet exist on `main` if
  B25-C is not merged. Test discovery (`--list`) succeeds regardless;
  full execution requires the B25-C pages to be live. This is the same
  trade-off as Iter 23 where the wizard was assumed to exist.
- **No real GPS hardware.** `mockGeolocation` returns a fixed Bangkok
  coordinate. Tests do NOT exercise:
   - PERMISSION_DENIED branch (user blocked the prompt)
   - TIMEOUT branch (slow GPS lock)
   - "Out of radius" branch (>500m from the farm)
   These are unit-test territory in B25-B / `audit-field-tools.tsx`.
- **No multipart-body assertion.** The photo-upload mock accepts ANY
  multipart payload and returns success. Validation that the file size
  / mime type / EXIF data made it server-side is left to B25-B unit
  tests — Playwright would need to parse the multipart envelope, which
  is overkill for the smoke pass.
- **No reassignment path.** Iter 25 covers only the happy-path
  scheduler → auditor → PASS decision. The reassignment screen
  (`/provider/scheduler/reassign`) already exists from a prior wave but
  is not yet under E2E coverage.
- **Mobile viewports not validated.** The new spec runs on chromium in
  CI; mobile-Chrome/mobile-Safari projects are listed but unvalidated.
  Cross-browser run remains on the roadmap shared with Iter 23.
