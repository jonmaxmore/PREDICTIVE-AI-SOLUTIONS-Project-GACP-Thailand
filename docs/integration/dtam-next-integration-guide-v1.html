แพลตฟอร์มรับรองมาตรฐาน GACP · กรมการแพทย์แผนไทยและการแพทย์ทางเลือก (DTAM)

คู่มือเชื่อมต่อ API สำหรับระบบ DTAM Next

Partner Interoperability API — ตรวจสอบที่มาที่ไปของ QR / รหัสสินค้า และเข้าถึงระบบ Trace (ต้นน้ำ → กลางน้ำ/ปลายน้ำ)
เวอร์ชันเอกสาร: 1.0 วันที่: 8 กรกฎาคม 2569 (2026) สถานะ API: ใช้งานจริงบน Production จัดทำโดย: Predictive AI Solution Co., Ltd. (ผู้ให้บริการแพลตฟอร์ม)

1. ภาพรวม

แพลตฟอร์ม GACP เป็นระบบต้นน้ำของห่วงโซ่ข้อมูลสมุนไพร — เก็บข้อมูลตั้งแต่การรับรองฟาร์ม (ใบรับรอง GACP), รอบการปลูก, ต้นพืชรายต้น (1 ต้น = 1 QR), การเก็บเกี่ยว (batch) จนถึงล็อตบรรจุ (lot) พร้อมชั้นความเชื่อมั่นเชิงคริปโต (ลายเซ็น RSA-SHA256 + hash chain)

ระบบ DTAM Next (กลางน้ำ/ปลายน้ำ) เชื่อมต่อผ่านชุด API นี้เพื่อ (ก) ตรวจสอบว่า QR หรือรหัสใด ๆ ที่พบ มีที่มาที่ไปอย่างไร และ (ข) เข้าถึงข้อมูลทะเบียนใบรับรอง/การเพิกถอน/เหตุการณ์ trace แบบ machine-to-machine

สภาพแวดล้อมBase URL
Productionhttps://gacpth.com/api/interoperability
Staging (สำหรับทดสอบ integration)https://staging.gacpth.com/api/interoperability

2. การยืนยันตัวตนและข้อกำหนดการใช้งาน

  • Endpoint กลุ่ม PARTNER ต้องส่ง header x-api-key: <secret> — secret ออกให้ต่อหน่วยงาน (partner id: dtam-next) โดยผู้ดูแลแพลตฟอร์ม; ไม่มี key หรือ key ผิด → 401 เสมอ (fail-closed)
  • Endpoint กลุ่ม PUBLIC เรียกได้โดยไม่ต้องมี key (โควตากลาง 1,000 req/15 นาที/IP)
  • โควตากลุ่ม PARTNER: 120 requests / 15 นาที ต่อหน่วยงาน (แยกจาก IP — ใช้ NAT ร่วมกันได้)
  • ทุกการเรียกของ partner ถูกบันทึก access log (หน่วยงาน, endpoint, รหัสที่ค้น, ผลลัพธ์) เพื่อการตรวจสอบย้อนหลังร่วมกัน
  • การส่งข้อมูล: REST / JSON / UTF-8 · ทุกคำตอบมี field success

3. Endpoint หลัก — ตรวจสอบที่มาที่ไปของรหัสใด ๆ (Universal Resolver)

PARTNER GET /v1/resolve?code=<สตริงที่สแกน/รหัส/URL>

ส่งอะไรมาก็ได้ที่พบบนสินค้า/เอกสาร — ระบบจำแนกชนิดและตอบที่มาที่ไปครบในคำขอเดียว:

รูปแบบที่รองรับจำแนกเป็น
GACP-* (เช่น GACP-TH-2569-A3F7B2)ใบรับรอง (CERTIFICATE)
UNIT-* (รหัสต้น) / PU-* (QR ต้น)ต้นพืชรายต้น (PLANT_UNIT)
BATCH-* / BT-*ล็อตเก็บเกี่ยว (HARVEST_BATCH)
LOT-*ล็อตบรรจุ (PACKAGING_LOT) ก่อน แล้วจึงตรวจ batch รูปแบบเก่า
UUID เปล่าตรวจดัชนี QR-seal ก่อน แล้วไล่ตามลำดับที่กำหนดในเอกสารสัญญา
URL เต็มจาก QR (…/trace/plant/…, …/verify/… ฯลฯ)normalize อัตโนมัติแล้วจำแนกตามชนิด

ตัวอย่างจริง: สแกน QR ต้นพืช → ล็อตไหน แปลงไหน รอบนี้ปลูกกี่ต้น ฟาร์มอะไร

  • ต้นที่ยังไม่เก็บเกี่ยว → "batch": null, "lots": []
  • รหัสที่ไม่รู้จัก → 404 พร้อม {"resolved": false, "probed": [...]} (รายการที่ระบบลองค้นแล้ว)
  • ระบบขัดข้อง → 500 เท่านั้น — จะไม่ตอบ "ไม่พบ" ปลอม ๆ

4. Endpoint ทั้งหมด

กลุ่มEndpointใช้ทำอะไร
PGET /v1/resolve?code=จำแนกรหัสใด ๆ + ที่มาที่ไปครบในคำขอเดียว (ข้อ 3)
PGET /v1/trace/events/{type}/{id}timeline เหตุการณ์ของ entity — type: CERTIFICATE, PLANTING_CYCLE, HARVEST_BATCH, PACKAGING_LOT, PLANT_UNIT (id รับทั้ง id/เลขที่/qrCode)
PGET /v1/trust/registryทะเบียนใบรับรอง (แบ่งหน้า, ค้นหา, กรองจังหวัด/สถานะ) สำหรับ sync
PGET /v1/trust/revocations?since=feed การเพิกถอนใบรับรอง (REVOCATION_TRANSPARENCY)
PGET /v1/certificates/{no}/e-certificateใบรับรองอิเล็กทรอนิกส์แบบมีลายเซ็น RSA-SHA256
PGET /v1/certificates/{no}/signed-envelopeเหมือนข้างบน + แนบ public key ในตัว
PUBGET /v1/verification?certificateNumber=ตรวจสถานะใบรับรอง (trustStatus: ACTIVE/REVOKED/EXPIRED/INVALID)
PUBGET /v1/trust/public-keypublic key + fingerprint สำหรับตรวจลายเซ็น
PUBPOST /v1/signatures/verifyตรวจลายเซ็นเอกสาร (payload/payloadHash + signature)
PUBGET /v1/data-contracts/traceability
GET /v1/event-contracts/trace-events		data contract / event contract ฉบับ machine-readable
ข้อกำหนดฝั่ง client: ต้องทนต่อค่า trustStatus ที่ไม่อยู่ใน 4 ค่าหลัก (ระบบอาจส่งสถานะดิบผ่านมาได้) และ eventId ของ trace events ไม่คงที่ระหว่างคำขอ — ใช้ entityId + eventType + occurredAt ในการ dedupe

5. การทดสอบด้วย Postman

  1. Import 3 ไฟล์จากชุดส่งมอบ: gacp-partner-api.postman_collection.json + environment (staging/production)
  2. เลือก environment staging → ตั้งค่าตัวแปร apiKey = secret ที่ได้รับ

6. ขั้นตอนขอรับ API key (production)

  1. หน่วยงานแจ้งความประสงค์ต่อผู้ดูแลแพลตฟอร์ม (owner) พร้อมระบุ partner id ที่ต้องการ (แนะนำ dtam-next)
  2. ผู้ดูแลออก secret (สุ่ม 64 hex) และส่งมอบผ่านช่องทางปลอดภัย — secret จะไม่แสดงซ้ำ
  3. ทดสอบ: curl -H "x-api-key: <secret>" https://gacpth.com/api/interoperability/v1/trust/registry → ต้องได้ 200
  4. การหมุน key: แจ้งผู้ดูแลเพื่อออก secret ใหม่และยกเลิกตัวเดิม

7. ข้อจำกัดของเวอร์ชันปัจจุบัน (v1)

  • ยังไม่มี endpoint sync แบบ incremental (cursor/since ครบทุก feed) — ใช้ registry แบบแบ่งหน้า + revocations ?since=
  • trace events สังเคราะห์จากข้อมูล ณ เวลาเรียก — ไม่มีลายเซ็นราย event (ใบรับรองอิเล็กทรอนิกส์มีลายเซ็นเต็มรูปแบบ)
  • ข้อมูลการปลูก/QR ต้นพืชบน production จะทยอยเพิ่มตามการใช้งานจริงของเกษตรกร — staging มีชุดทดสอบครบทุกชนิดแล้ว
