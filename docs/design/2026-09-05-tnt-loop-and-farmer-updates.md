## 0. ทำไมยังไม่ครบ loop — สามช่องที่พบจากการอ่านโค้ดจริงวันนี้

### 0.1 ไม่มีหน้าจอให้เกษตรกรแก้ข้อมูลรอบปลูกเลย

`apps/web-app/src/lib/services/planting-service.ts:136` มี `updateCycle()` เรียก
`PATCH /planting-cycles/:id` — **แต่ไม่มีไฟล์ไหนในทั้ง `apps/web-app/src` เรียกฟังก์ชันนี้**
ประตูฝั่ง server เปิดอยู่และเจ้าของเรียกได้ผ่าน API แต่ในหน้าเว็บไม่มีปุ่ม

หน้าที่มีจริงใต้ `/health/planting` มีสี่หน้า: รายการ · สร้างใหม่ · รายละเอียด · บันทึกกิจกรรม ·
ป้ายแปลง — **ไม่มีหน้า "แก้ไข"** ดังนั้นข้อ R11/R12 ("แก้ได้จนตัด") ยังไม่เคยถูกใช้งานจริง

### 0.2 ด่านแช่แข็งมีอยู่จริง แต่รั่วห้าฟิลด์ — และสี่ในห้าขึ้นหน้าสาธารณะ

`services/planting-service.js:366` คำนวณ `isLocked` ถูกต้อง (สถานะ HARVESTED/COMPLETED
หรือมี batch แล้ว) แต่บล็อกที่คัดลอกค่าลง `updateData` **อยู่เหนือ `if (!isLocked)`**:

```js
const metadataFields = ['notes', 'seedSource', 'varietyName', 'irrigationType', 'soilType'];
for (const field of metadataFields) {
    if (data[field] !== undefined) { updateData[field] = data[field]; }
}
if (!isLocked) { /* ...ที่เหลือถึงจะถูกกัน... */ }
```

สี่ในห้าฟิลด์นี้ถูกส่งออกหน้าสาธารณะที่ไม่ต้องล็อกอิน
(`services/trace-service/resolve-generic.js:150,155,156,157` → `variety`, `seedSource`,
`soilType`, `irrigationType`)

**ผลที่ตามมา**: หลังตัดแล้ว หลังพิมพ์ QR แล้ว หลังของออกสู่ตลาดแล้ว เจ้าของรอบปลูกยังแก้
**สายพันธุ์** และ **แหล่งที่มาของเมล็ด** ที่หน้าสแกนสาธารณะประกาศอยู่ได้ — เงียบ ๆ ไม่มี record
นี่คือสิ่งที่ Track & Trace มีไว้เพื่อป้องกันโดยตรง

### 0.3 แต่สองประตูปลายทางทำถูกแล้ว — และเป็นแบบที่ควรใช้ทั้งสามชั้น

| ชั้น | สถานะวันนี้ | หลักฐาน |
|---|---|---|
| **ล็อตบรรจุ** | ✅ ถูกต้อง — พิมพ์ QR แล้วแก้ไม่ได้ ปฏิเสธ 403 พร้อมข้อความไทย · มี allow-list ก่อนพิมพ์ | `routes/api/trace/lots.js:387,395` |
| **รุ่นเก็บเกี่ยว** | ✅ ถูกต้อง — น้ำหนักและวันเก็บเกี่ยวแช่แข็งเมื่อออกล็อตแล้ว **ปฏิเสธเสียงดัง ไม่ตัดคีย์เงียบ ๆ** | `services/harvest-service.js` `FROZEN_ONCE_PACKED` |
| **รอบปลูก** | ❌ ล็อกบางส่วน แล้ว**ตัดคีย์เงียบ ๆ** | `services/planting-service.js:366-372` |

คอมเมนต์ในโค้ดของชั้นรุ่นเก็บเกี่ยวเขียนเหตุผลไว้เองแล้ว: *"Refuse loudly rather than dropping
the keys silently. A farmer editing notes and a weight in one request must not be told the
whole edit succeeded when half of it was discarded"* — ชั้นรอบปลูกทำสิ่งที่คอมเมนต์นี้ห้ามไว้

**แบบอ้างอิงจึงมีอยู่แล้วในรีโปนี้** ไม่ต้องคิดใหม่ ต้องทำให้ครบสามชั้นเท่านั้น

## 1. loop เต็ม — ของจริงเจ็ดขั้น

```
1. ขออนุญาต (กทล.1)  →  2. ใบรับรอง GACP  →  3. เปิดรอบปลูก [QR ①]
                                                      ↓
        7. สแกน  ←  6. บรรจุล็อต [QR ③]  ←  5. เก็บเกี่ยว [QR ②]  ←  4. บันทึกกิจกรรม
```

| ขั้น | ใครทำ | เขียนอะไร | แก้ได้ถึงเมื่อไร |
|---|---|---|---|
| 1 ขออนุญาต | เกษตรกร | แบบ กทล.1 + เอกสารแนบ | จนกดยื่น · หลังยื่นแก้ผ่านรอบขอแก้ไขเท่านั้น |
| 2 ใบรับรอง | ระบบ (หลังตรวจผ่าน) | เลขใบรับรอง + ลายเซ็นดิจิทัล | แก้ไม่ได้ · เพิกถอนได้โดยผู้มีอำนาจ |
| 3 เปิดรอบปลูก | เกษตรกร | แปลง พื้นที่ พืช สายพันธุ์ วันปลูก | **จนวันตัด** |
| 4 บันทึกกิจกรรม | เกษตรกร | รดน้ำ ใส่ปุ๋ย ป้องกันโรค | **เพิ่มได้เสมอ ทับของเดิมไม่ได้** |
| 5 เก็บเกี่ยว | เกษตรกร | น้ำหนักสด/แห้ง วันเก็บเกี่ยว | จนออกล็อตใบแรก |
| 6 บรรจุล็อต | เกษตรกร | น้ำหนักบรรจุ วันบรรจุ | จนพิมพ์ QR |
| 7 สแกน | ใครก็ได้ ไม่ต้องล็อกอิน | — | อ่านอย่างเดียว |

**ขั้นที่ 3 คือขั้นเดียวที่ยังไม่มีหน้าจอ** และเป็นขั้นที่ประตูรั่ว

## 2. หน้าที่ขาด — "แก้ไขรอบปลูก" (ออกแบบใหม่)

### 2.1 สามสถานะที่หน้าจอต้องบอกให้ชัด ก่อนกดอะไรทั้งนั้น

| สถานะ | เงื่อนไข | หน้าจอแสดง |
|---|---|---|
| **แก้ได้** | ยังไม่ตัด ยังไม่มีรุ่นเก็บเกี่ยว | ฟอร์มปกติ + บอกว่า "แก้ได้จนถึงวันเก็บเกี่ยว" |
| **แช่แข็งแล้ว** | ตัดแล้ว หรือมีรุ่นเก็บเกี่ยวแล้ว | ฟอร์มอ่านอย่างเดียว + ปุ่ม "ขอแก้ไขข้อมูลที่แช่แข็ง" |
| **อ่านไม่ได้** | ระบบตอบไม่ได้ | บอกว่าอ่านไม่ได้ **ห้ามแสดงเหมือนช่องว่าง** (หลักข้อ 4 ของ scope doc) |

### 2.2 อะไรแก้ได้ตอนไหน — ตารางเดียว บังคับทั้งสองฝั่ง

| ฟิลด์ | ก่อนตัด | หลังตัด | ขึ้นหน้าสาธารณะไหม |
|---|---|---|---|
| `cycleName` ชื่อรอบ | ✅ | ❌ | ❌ (มติ 2026-09-05 ไม่เปิด) |
| `varietyName` สายพันธุ์ | ✅ | ❌ **← วันนี้แก้ได้ ต้องปิด** | ✅ |
| `seedSource` แหล่งเมล็ด | ✅ | ❌ **← วันนี้แก้ได้ ต้องปิด** | ✅ |
| `soilType` · `irrigationType` | ✅ | ❌ **← วันนี้แก้ได้ ต้องปิด** | ✅ |
| `expectedHarvestDate` | ✅ | ❌ | ❌ |
| `status` | ✅ (ในชุดปิด 6 ค่า) | ❌ | ทางอ้อม |
| แปลงที่ผูก | ✅ (กติกา R15) | ❌ | ❌ |
| `notes` บันทึกภายใน | ✅ | ✅ | ❌ — ไม่เคยส่งออก จึงไม่ใช่คำกล่าวอ้างต่อผู้ซื้อ |

`notes` คือฟิลด์เดียวที่ยังแก้ได้หลังแช่แข็ง เพราะเป็นบันทึกของเกษตรกรถึงตัวเอง ไม่ปรากฏบนหน้าสแกน
ไม่ใช่คำกล่าวอ้างต่อผู้ซื้อ — ต่างจากอีกสี่ฟิลด์ที่กองอยู่ในลิสต์เดียวกันวันนี้โดยไม่มีเหตุผลแยกแยะ

### 2.3 หลังแช่แข็งแล้ว **ไม่มีใครแก้ได้เลย** — มติ operator 2026-09-05

ถามไปว่าใครควรมีอำนาจอนุมัติคำขอแก้ข้อมูลที่แช่แข็ง ระหว่างผู้ตรวจเอกสารกับพนักงานติดตาม
คำตอบคือ **"ไม่มีสิทธิ์ทั้งหมด"**

⇒ **ไม่มีเส้นทางขอแก้ไขข้อมูลที่แช่แข็ง** ไม่มีหน้าจอขออนุมัติ ไม่มีบทบาทไหนอนุมัติได้
แช่แข็งแล้วคือแช่แข็งจริง ไม่มีข้อยกเว้น

นี่เข้มกว่าที่ผมออกแบบไว้ตอนแรก และแข็งแรงกว่า — ระบบที่มี "ทางพิเศษสำหรับกรณีจำเป็น"
คือระบบที่ทางพิเศษนั้นถูกใช้จนกลายเป็นทางปกติ · การไม่มีประตูเลย ไม่มีอะไรให้กดดันใครให้เปิด

**แล้วถ้าข้อมูลผิดจริงล่ะ** — ตอบด้วยการ **เพิ่ม ไม่ใช่ทับ** ซึ่งเป็นกลไกที่มีอยู่แล้ว:

| ผิดตรงไหน | ทำอย่างไร |
|---|---|
| บันทึกกิจกรรมลงผิด | ลงรายการแก้ไข**เพิ่ม** อ้างรายการเดิม — ของเดิมยังอยู่ ประวัติครบ |
| ผลแลปมาทีหลัง | อัปโหลด COA **เพิ่ม** (§4.5) — เป็นการเพิ่มเอกสาร ไม่ใช่แก้ค่าที่ประกาศไว้ |
| ได้ COA ฉบับใหม่ที่ต่างจากเดิม | อัปโหลด**เพิ่ม** ทั้งสองฉบับแสดงคู่กันพร้อมวันที่ · **ไม่ลบของเดิม** |
| สายพันธุ์/แหล่งเมล็ดที่ประกาศไปแล้วผิด | **แก้ไม่ได้** — รอบปลูกนั้นจบไปแล้ว ของออกตลาดไปแล้ว การเขียนประวัติใหม่คือสิ่งที่ T&T มีไว้ป้องกัน |

แถวสุดท้ายคือราคาของมติข้อนี้ และเป็นราคาที่ตั้งใจจ่าย: **ความถูกต้องของสิ่งที่ประกาศไปแล้ว
มีค่ามากกว่าความสะดวกของคนที่กรอกผิด** ทางแก้ที่แท้จริงคือกันไม่ให้กรอกผิดตั้งแต่ก่อนตัด
ซึ่งคือหน้าที่ของหน้าจอในข้อ 2.1-2.2


### 2.4 กิจกรรม (ขั้นที่ 4) — เพิ่มได้เสมอ ทับไม่ได้เลย

บันทึกกิจกรรมเป็นสมุดบันทึก ไม่ใช่แบบฟอร์ม · การใส่ปุ๋ยเมื่อวันจันทร์เป็นข้อเท็จจริงที่เกิดแล้ว
การ "แก้" มันคือการเขียนประวัติใหม่ · ถ้าลงผิด ให้ลงรายการแก้ไขเพิ่ม อ้างรายการเดิม
(§7.4 ของสเปก 2026-08-20 สั่งไว้แล้ว — ยังไม่มีด่านบังคับ)

## 3. ขอบเขตข้อมูลสามชั้น — พร้อมฐานทางกฎหมาย

> ฐานกฎหมายของ**ตัวใบอนุญาต**: พ.ร.บ.คุ้มครองและส่งเสริมภูมิปัญญาการแพทย์แผนไทย พ.ศ. 2542
> ม.44-46 (ตามที่ `docs/requirements/gacp-document-requirements-research.md:4` อ้างไว้)
> ฐานกฎหมายของ**การเปิดเผยข้อมูล**: พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA)

### 3.1 ชั้นเปิด — สแกนได้โดยไม่ล็อกอิน

> **มติ operator 2026-09-05 (แทนที่ข้อความเดิมทั้งย่อหน้า)**
> *"ยังไม่ต้องสนใจกฎหมาย PDPA ให้อัปโหลด COA และพวกชื่อฟาร์ม และที่อยู่ติดต่อได้ เมื่อสแกนต้องเห็นทั้งหมด"*

หลักของเฟสนี้คือ **คนสแกนเห็นทั้งหมด**:

| ข้อมูล | เปิด |
|---|---|
| เลขและสถานะใบรับรอง · ชนิดพืช สายพันธุ์ · วันปลูก วันเก็บเกี่ยว น้ำหนักจริง | ✅ (เหมือนเดิม) |
| **ชื่อฟาร์ม** | ✅ **เปิดแล้ว** — แสดงเต็ม ไม่ mask ไม่ต้องตั้งชื่อแสดงแยก |
| **ที่อยู่ / ข้อมูลติดต่อเกษตรกร** | ✅ **เปิดแล้ว** — แสดงเสมอ ไม่ใช่ opt-in |
| **ไฟล์ COA + ค่าผลตรวจ** | ✅ **เปิดแล้ว** — แทนที่ R9 ที่เคยให้เปิดแค่ "มี/ไม่มี" |
| ตัวเลขคาดการณ์ผลผลิต · ชื่อแปลง · ชื่อรอบปลูก · id ภายใน | ❌ คงเดิม — ไม่ใช่เรื่อง PDPA แต่เป็นความลับทางธุรกิจและมือจับสำหรับไล่เดา |
| **พิกัด GPS** | ❌ **ยืนยันแล้ว 2026-09-05: ไม่เปิด** |

การผ่อนนี้เป็นแบบเดียวกับที่ operator เคยผ่อนกฎ residency: **ผ่อนสำหรับเฟสเดโม
และต้องกลับมาทบทวนก่อนขึ้นเครื่องจริงของกระทรวง** รายการที่ต้องกลับมาอยู่ที่
`tnt-data-scope.md` §7 เพื่อไม่ให้ "ผ่อนชั่วคราว" กลายเป็น "ลืมไปเลย"

**พิกัด GPS — operator ยืนยัน 2026-09-05: ไม่เปิด** · ต่างจากสามข้อบนตรงที่ไม่ใช่เรื่อง
ความเป็นส่วนตัว แต่เป็น**ความปลอดภัยทางกายภาพ** พิกัดพาคนไปถึงแปลงได้ และแปลงกัญชาเป็นเป้าการโจรกรรม ·
ที่ตั้งระดับตำบล/อำเภอ/จังหวัดยังเปิดตามเดิมและตรวจสอบที่มาได้จริง — โค้ดทำถูกอยู่แล้ว ไม่ต้องแก้

### 3.2 ชั้นเกษตรกร — เจ้าของข้อมูล

ตาราง §2 ของ scope doc ยังใช้ได้ทั้งหมด · **มติ 2026-09-05 ปิดข้อ 5.2 ที่ค้าง**:

> **เกษตรกรเห็นบันทึกของผู้ตรวจเกี่ยวกับตนได้** — operator: *"อ้างอิงตามกฎหมาย PDPA ได้เลย"*

PDPA **ม.30** ให้เจ้าของข้อมูลมีสิทธิขอเข้าถึงและขอรับสำเนาข้อมูลส่วนบุคคลของตน รวมถึงขอให้
เปิดเผยถึงการได้มาซึ่งข้อมูลที่ตนไม่ได้ให้ความยินยอม · บันทึกที่ผู้ตรวจเขียน**เกี่ยวกับเกษตรกรราย
นั้น**จึงเป็นข้อมูลส่วนบุคคลของเกษตรกร และเปิดให้เจ้าตัวดูได้เป็นค่าตั้งต้น

ข้อยกเว้นที่ต้องเผื่อไว้ ไม่ใช่ทั้งหมดจะเปิดได้: ม.30 วรรคสองให้ปฏิเสธได้เมื่อ**เป็นไปตามกฎหมาย
หรือคำสั่งศาล หรือกระทบสิทธิเสรีภาพของบุคคลอื่น** — ในทางปฏิบัติแปลว่า บันทึกที่พาดพิงบุคคลที่สาม

ระบบจึงต้องมีสวิตช์รายรายการ ไม่ใช่เปิดหมดหรือปิดหมด

### 3.3 ชั้นพนักงานติดตาม — **มติ 2026-09-05: ทุกฟาร์มทั้งประเทศ**

> operator: *"เห็นข้อมูลทั้งหมด"* + *"ฟาร์มทุกประเทศ"*

⇒ ตาราง §3 ของ scope doc ที่เสนอให้จำกัดเฉพาะฟาร์มที่ได้รับมอบหมาย และให้ mask เลขบัตร

| PII เกษตรกร · เลขบัตรประชาชนเต็ม · ไฟล์แนบ | ✅ | ตามมติ |

**สิ่งที่มตินี้ไม่ได้ยกเลิก และยังบังคับอยู่ — เพราะเป็นคนละคำถามกับ "เห็นได้แค่ไหน"**:

ยิ่งขอบเขตกว้าง หน้าที่ตามกฎหมายยิ่งหนัก ไม่ใช่เบาลง PDPA วางหน้าที่ไว้ที่**ผู้ควบคุมข้อมูล**
ซึ่งคือแพลตฟอร์ม ไม่ใช่ที่ตัวพนักงาน:

1. **ม.37(1)** — ต้องจัดให้มีมาตรการรักษาความมั่นคงปลอดภัยที่เหมาะสม และ**ป้องกันการเข้าถึง
   หรือใช้โดยมิชอบ** · สิทธิ์ที่กว้างระดับทั้งประเทศโดยไม่มีเครื่องตรวจ ไม่ผ่านข้อนี้
2. **ม.39** — ต้องบันทึกรายการอย่างน้อยประกอบด้วยข้อมูลที่เก็บ วัตถุประสงค์ และ**การเข้าถึง**
   ⇒ **ทุกการเปิดดูฟาร์มที่ตนไม่ได้รับมอบหมาย ต้องบันทึกว่าใครเปิดของใครเมื่อไร**
   นี่ไม่ใช่การจำกัดขอบเขต แต่เป็นการทำให้ขอบเขตที่กว้างนั้นตรวจสอบย้อนหลังได้
3. **หน้าจอต้องบอกพนักงานว่ากำลังถูกบันทึก** — ไม่ใช่เพื่อขู่ แต่เพราะการเปิดดูที่รู้ตัวว่าถูกบันทึก
   กับที่ไม่รู้ตัว เป็นการกระทำคนละอย่างกันในทางวินัย

**ข้อเสนอเชิงปฏิบัติ (ยังไม่ใช่มติ)**: แยก "ค้นหาฟาร์มทั้งประเทศ" ออกจาก "งานที่ได้รับมอบหมาย"
เป็นสองเมนู · เมนูแรกบันทึก audit ทุกครั้งที่เปิด · เมนูหลังเป็นงานประจำวันไม่ต้องเตือนอะไร
ได้ทั้งขอบเขตตามมติและหลักฐานตาม ม.39 โดยไม่กวนงานปกติ

## 4.5 ผลแลป — ตัวอย่างไปกับ QR ใบไหน และแนบผลที่ไหน

### QR ที่แปะถุงตัวอย่างส่งแลป คือ **ตัวตนที่ ② (รุ่นเก็บเกี่ยว)**

ตัวอย่างถูกเก็บจากรุ่นที่กำลังตาก **ก่อนบรรจุ** · ① คือที่ดิน มันไม่เดินทางไปไหน ·
③ ถุงบรรจุยังไม่เกิด และถ้ารอตรวจหลังบรรจุ ผลไม่ผ่านก็แก้อะไรไม่ได้แล้ว ของถูกซีลไปแล้ว

การตรวจมีสองจังหวะ และหมายความคนละอย่าง:

| จังหวะ | แปะ QR | ผลใช้ตัดสินอะไร |
|---|---|---|
| **ก่อนบรรจุ — ที่รุ่น** | ② | รุ่นนี้บรรจุขายได้ไหม · เป็นจังหวะที่ผลตรวจยังเปลี่ยนการตัดสินใจได้ |
| **หลังบรรจุ — ที่ล็อต** | ③ | COA ผูกกับล็อตที่ผู้ซื้อได้รับจริง — ผู้ซื้อบางราย/การส่งออกต้องการแบบนี้ |

**ทั้งสองจังหวะต้องมี ไม่ใช่เลือกอย่างใดอย่างหนึ่ง** — จังหวะแรกคือการควบคุมคุณภาพ
จังหวะหลังคือเอกสารประกอบสินค้า

### ⚠️ วันนี้มีแค่จังหวะหลัง และไม่มีหน้าอัปโหลด

| สิ่งที่ควรมี | สถานะจริง |
|---|---|
| โมเดล `BatchLabResult` (สเปก 2026-08-20 §4.3 สั่งไว้) | **ไม่มีในรีโปเลย — 0 ไฟล์** |
| ฟิลด์ผลแลปบน HarvestBatch | **ไม่มี** |
| ฟิลด์ผลแลปบน Lot | ✅ มี — `labTestReportUrl`, `thcContent`, `cbdContent`, `moistureContent`, `testStatus` (`trace.prisma:31-35`) |
| หน้าจอให้เกษตรกรอัปโหลด COA | **ไม่มี** — ค่าเข้ามาเป็นฟิลด์ใน body ของ POST/PUT ล็อต (`lots.js:79,153,340`) |
| หน้าสาธารณะ | เดิมเปิดแค่ `tested: true/false` (`resolve-generic.js:355-358`) — **มติ 2026-09-05 สั่งให้เปิดไฟล์ COA และค่าผลตรวจด้วย** ⇒ ต้องแก้ ไม่ใช่ปล่อยไว้ |

**ไม่ใช่ "มีแค่ติ๊กว่ามีผลแลป"** — ระบบเก็บ file pointer จริง ค่าตัวเลขจริง และสถานะผ่าน/ไม่ผ่าน
สิ่งที่ขาดคือ **ประตูให้เกษตรกรใส่มันเข้าไป** และ **ที่ยึดของผลตรวจระดับรุ่น**

### มติ operator 2026-09-05 — แนบ COA หลังได้ผล แล้วค่อยพิมพ์ป้าย

> *"ต้องหาทางแนบผลแลปให้ได้ เราจะไม่ได้พิมพ์บอกค่าเท่าไหร่ เราจะอัพโหลดผลแลป
> ต้องอัพโหลดในขั้นตอนไหน หรือว่าอัพโหลดได้หลังได้รับ COA เพื่อทำ print"*

**คำตอบ: ใช่ และลำดับที่คุณเสนอแก้ปัญหาที่รายงานไว้ข้างบนได้พอดี** โดยไม่ต้องแตะการแช่แข็งเลย

```
เก็บเกี่ยว → พิมพ์ป้ายรุ่น [QR ②] → เก็บตัวอย่างแปะ QR ② ส่งแลป
                                        ↓ 3-14 วัน
                              COA กลับมา → อัปโหลดใส่ "รุ่น"
                                        ↓
                              บรรจุ → พิมพ์ป้ายล็อต [QR ③]
```

เส้นตายที่เคยชนกันหายไป เพราะ **QR ที่ต้องพิมพ์ก่อนส่งแลปคือ ② ไม่ใช่ ③**
② พิมพ์ตอนเก็บเกี่ยวซึ่งเกิดก่อนอยู่แล้ว ส่วน ③ พิมพ์หลังบรรจุ ซึ่งเกิดหลัง COA กลับมา
⇒ ไม่มีขั้นไหนต้องแก้ของที่แช่แข็งไปแล้ว

### COA ผูกกับ **รุ่น** ไม่ใช่ล็อต

| ผูกกับ | ผลที่ตามมา |
|---|---|
| **รุ่น (②) — เลือกอันนี้** | ห้องแลปตรวจรุ่น ไม่ได้ตรวจถุง · หนึ่งรุ่นออกได้หลายล็อต แนบครั้งเดียวทุกล็อตได้รับสืบทอด |
| ล็อต (③) | ต้องอัปโหลดไฟล์เดิมซ้ำทุกล็อต และวันหนึ่งจะไม่ตรงกัน |

**และการอัปโหลดเป็นการ *เพิ่ม* ไม่ใช่การ *แก้*** — จึงไม่ชนกับการแช่แข็งน้ำหนักของรุ่น
(`FROZEN_ONCE_PACKED` คุมน้ำหนักกับวันเก็บเกี่ยว ไม่ได้คุมเอกสารแนบ) · COA คือเอกสารที่มาถึงทีหลัง
ไม่ใช่การแก้สิ่งที่เคยประกาศไว้ · **COA ที่แนบไปแล้วเปลี่ยนไม่ได้และลบไม่ได้** (มติข้อ 2.3) —
ถ้ามีฉบับใหม่ ให้อัปโหลด**เพิ่ม** ทั้งสองฉบับแสดงคู่กันพร้อมวันที่ ให้ผู้อ่านเห็นเองว่าเกิดอะไรขึ้น

### ไม่พิมพ์ค่าเอง — ไฟล์คือหลักฐาน

> operator: *"เราจะไม่ได้พิมพ์บอกค่าเท่าไหร่ เราจะอัพโหลดผลแลป"*

⇒ **ไม่มีช่องกรอก THC / CBD / ความชื้น** ทั้งบนหน้าจอและที่ประตู API
คอลัมน์ `thcContent` · `cbdContent` · `moistureContent` บน `Lot` ยังอยู่สำหรับข้อมูลเก่า
แต่ไม่รับค่าที่พิมพ์มือใหม่อีก

เหตุผลตรงกับที่ operator เคยสั่งเรื่อง hardcode: ตัวเลขที่คนพิมพ์เองคือตัวเลขที่พิมพ์ผิดได้
และเมื่อมันขัดกับไฟล์ COA จะไม่มีใครรู้ว่าอันไหนจริง — **ไฟล์เดียวเป็นแหล่งความจริงเดียว**

### COA ต้องขึ้นหน้าสแกน — มติ operator 2026-09-05

> *"เดี๋ยวตอนทำ T&T ต้องแนบเอกสารนี้ลงไปด้วย ให้เห็นว่าฟาร์มนี้มีผลตรวจ"*

⇒ หน้าสแกนแสดง **สองอย่างที่ต้องแยกกันให้ขาด** ไม่ใช่อย่างเดียว

| แสดงอะไร | เกี่ยวกับ | ทำไมต้องแยก |
|---|---|---|
| **ล็อตนี้: มีผลตรวจ / ยังไม่มีผลตรวจ** + ปุ่มเปิดไฟล์ COA | ของที่อยู่ในมือคนสแกน | นี่คือคำถามที่เขามาถาม |
| **ฟาร์มนี้: มีผลตรวจแล็บ N ฉบับ** | ประวัติของฟาร์ม | ตอบคำสั่ง "ให้เห็นว่าฟาร์มนี้มีผลตรวจ" |

**กับดักที่ต้องกัน** — ถ้าเขียนรวมกันเป็น "ฟาร์มนี้มีผลตรวจ" อย่างเดียว คนที่ถือถุงซึ่ง
*ยังไม่มี* COA จะอ่านว่าถุงในมือผ่านการตรวจแล้ว ทั้งที่ไม่ใช่ · นั่นคือการทำให้คนเข้าใจผิด
ด้วยข้อความที่แต่ละประโยคเป็นความจริง ซึ่งแย่กว่าการไม่บอกอะไรเลย

**กติกาถ้อยคำ**: บรรทัดของล็อตต้องมาก่อนและเด่นกว่าเสมอ · บรรทัดของฟาร์มต้องมีคำว่า
"ฟาร์มนี้" หรือ "ทั้งฟาร์ม" ติดอยู่ทุกครั้ง ห้ามพูดลอย ๆ ว่า "มีผลตรวจ"

### ต้องตัดสิน — ไม่มี COA พิมพ์ป้ายล็อตได้ไหม

R7 (สเปก 2026-08-20) บอกว่าผลแลปเป็น optional ทั้งขา · มติวันนี้ไม่ได้ยกเลิกข้อนั้น จึงมีสองทาง:

| ทาง | ผล |
|---|---|
| **ก. คงตาม R7** — ไม่มี COA ก็พิมพ์ได้ หน้าสแกนบอกตามจริงว่า "ยังไม่มีผลตรวจ" | ยืดหยุ่น · ผู้ซื้อเห็นเองว่าล็อตไหนยังไม่มีผล |
