**แทนที่** `docs/design/finance-design-system-2026-05-16.md` และ `docs/design/pdf-samples-2026-05-16.md`
ทั้งสองฉบับเขียนใต้โมเดล two-money-flow ที่คำสั่ง W14 (2026-08-22) ยกเลิกแล้ว

## 0. ทำไมต้องออกแบบใหม่ ทั้งที่ระบบออกเอกสารได้อยู่แล้ว

ระบบออก PDF ได้ครบ แต่ **โครงของเอกสารยังเป็นของโมเดลที่มีผู้ออกสองราย**

| พบจริงในโค้ดวันนี้ | ทำไมเป็นปัญหา |
|---|---|
| `generateQuotationPdf({ issuerSide })` รับ `'DTAM' \| 'PLATFORM'` และ **ประตู `/applications/:id/quotations/:issuerType/pdf` รับค่าจาก path param** | `resolveAllowedIssuerSides` (`quotations.js:67`) ให้ทุก role ที่ไม่ใช่ account_dtam/account_platform เข้าถึงทั้งสองฝั่ง — เกษตรกรเจ้าของคำขอจึงเรียก `/quotations/DTAM/pdf` ได้เอง ทั้งที่กรมฯ ไม่ได้เป็นผู้ออกเอกสารแล้ว |
| template `government-revenue-receipt.html` (ใบเสร็จเงินรายได้แผ่นดิน ไม่มีบรรทัด VAT) | เป็นใบเสร็จในนามกรมฯ ซึ่ง W14 เลิกออก |
| `receipt-auto-sign-service` มี key namespace แยก `DTAM` / `PLATFORM` | ผนึกสองชุดสำหรับผู้ออกสองราย |
| `quotation-line-items.js:144` — ถ้าเป็นฝั่ง DTAM คืน VAT = 0 | จุดยืน "ส่วนรัฐยกเว้น VAT" ที่เลิกใช้แล้ว |

**หลักที่ใช้จริงตั้งแต่ W14**: บริษัทเป็นผู้ออกเอกสาร**รายเดียว** · VAT 7% บนค่าบริการทั้งก้อน ·
บริษัทจ่ายกรมฯ ภายหลังในฐานะต้นทุนของตนเอง (`docs/architecture/fee-model-2026-09-05.md`)

## 1. เอกสารมีกี่ใบ และแต่ละใบพูดอะไร

| # | เอกสาร | ออกเมื่อ | ผูกทางกฎหมายอย่างไร |
|---|---|---|---|
| 1 | **ใบเสนอราคา** (Quotation) | ตอนยื่นคำขอ / ตอนขึ้นงวดที่ 2 | **ข้อเสนอ** ยังไม่ก่อหนี้ · ผู้ยื่นกด "ยอมรับ" จึงผูกพัน · ราคาถูกแช่แข็งไว้ในใบ (snapshot) ราคาที่เปลี่ยนทีหลังไม่ย้อนกลับมาแก้ใบที่รับแล้ว |
| 2 | **ใบวางบิล / ใบแจ้งหนี้** (Invoice) | เมื่อใบเสนอราคาถูกยอมรับ | **การเรียกเก็บ** · ระบุยอด กำหนดชำระ และช่องทาง |
| 3 | **ใบเสร็จรับเงิน / ใบกำกับภาษีเต็มรูป** | เมื่อชำระสำเร็จ (webhook ยืนยันแล้วเท่านั้น) | **หลักฐานการชำระ + เอกสารภาษี** ตาม ป.รัษฎากร ม.86/4 · ผู้ซื้อที่จด VAT ใช้เครดิตภาษีซื้อได้ |

**ไม่มีใบที่ 4** — ไม่มีใบเสร็จในนามกรมฯ อีกต่อไป (W14)

### ใบลดหนี้ / ใบเพิ่มหนี้
ยังมี (ม.86/10, ม.86/9) แต่เป็นเอกสารแก้ไข ออกเมื่อยอดที่เรียกเก็บผิดหรือมีการคืนเงิน
ไม่ได้อยู่ในเส้นทางปกติ จึงไม่อยู่ในการออกแบบชุดนี้

## 2. โครงหน้ากระดาษ — เหมือนกันทั้งสามใบ

เอกสารสามใบใช้โครงเดียว ต่างกันที่หัวเรื่อง สถานะ และบล็อกท้าย
เหตุผลไม่ใช่ความสวยงาม: ผู้ยื่นคนหนึ่งจะเห็นทั้งสามใบตามลำดับ **ถ้าโครงต่างกัน
เขาต้องเรียนรู้การอ่านใหม่ทุกครั้ง** และการเทียบยอดข้ามใบทำได้ยากขึ้น

```
┌──────────────────────────────────────────────────────────────┐
│ [โลโก้]  บริษัท พรีดิกทีฟ เอไอ โซลูชัน จำกัด (สำนักงานใหญ่)      │
│          เลขประจำตัวผู้เสียภาษี 0105568045932                   │
│          429/69 หมู่บ้านพรีเมี่ยมเพลส ถนนสุคนธสวัสดิ์ ...        │
│                                                              │
│                    ใบเสนอราคา                    เลขที่ QT-…  │
│                    (QUOTATION)                   วันที่ …     │
├──────────────────────────────────────────────────────────────┤
│ ลูกค้า                                                        │
│   ชื่อ …                        เลขประจำตัวผู้เสียภาษี …        │
│   ที่อยู่ …                     คำขอเลขที่ APP-…              │
├──────────────────────────────────────────────────────────────┤
│ #  รายการ                              จำนวน   ราคา    รวม   │
│ 1  ค่าบริการดำเนินการรับรองมาตรฐาน GACP     1    5,000   5,000  │
│    (ราคาเต็ม) — งวดที่ 1 ตรวจเอกสาร                            │
│ 2  ค่าบริการแพลตฟอร์ม 10%                  1      500     500  │
├──────────────────────────────────────────────────────────────┤
│                                   รวมเป็นเงิน      5,500      │
│                                   ภาษีมูลค่าเพิ่ม 7%   385      │
│                                   ═══════════════════════      │
│                                   จำนวนเงินรวมทั้งสิ้น 5,885    │
│              (ห้าพันแปดร้อยแปดสิบห้าบาทถ้วน)                    │
├──────────────────────────────────────────────────────────────┤
│ [บล็อกท้าย — ต่างกันตามชนิดเอกสาร ดูข้อ 3]                     │
└──────────────────────────────────────────────────────────────┘
```

### กติกาของตารางรายการ
1. **ทุกบรรทัดเสียภาษี** — ไม่มีคอลัมน์ "ยกเว้น VAT" ไม่มีเชิงอรรถ ม.77/1(10)
   (ใบแจ้งหนี้เคยพิมพ์ข้อยกเว้นนี้ทั้งที่เก็บ VAT ไปแล้ว ต่างกัน 350 บาท/ใบ — แก้แล้ววันนี้)
2. **ชื่อบรรทัดเหมือนกันทั้งสามใบ** ผู้ยื่นเทียบใบเสนอราคากับใบเสร็จได้ทีละบรรทัด
3. **"ราคาเต็ม" ไม่ใช่ "ค่าธรรมเนียมกรมฯ"** — เกษตรกรซื้อบริการจากบริษัท ไม่ได้จ่ายค่าธรรมเนียมให้กรมฯ
4. **จำนวนคูณตามรูปแบบการปลูก** — 2 รูปแบบ = ยอดคูณสอง แสดงในคอลัมน์จำนวน ไม่ใช่ซ่อนในราคา
5. **ตัวเลขทุกตัวมาจาก `FEES` ตัวเดียว** ไม่มีค่าคงที่ในไฟล์เอกสาร (บังคับด้วย probe `fee-single-source`)
6. **เอกสารพูดกับลูกค้า ไม่พูดถึงตัวระบบ** — ห้ามพิมพ์ศัพท์ภายในลงบนใบ: "ยืนยันโดย webhook",
   "ลำดับต่อเนื่องตาม ม.86/4", ชื่อ service, ชื่อ state, feature flag · กติกาเหล่านั้นเป็นของระบบ
   อยู่ในเอกสารออกแบบฉบับนี้ · บนใบเขียนเฉพาะสิ่งที่ลูกค้าต้องใช้: วิธีชำระ อ้างอิงการชำระ ผู้รับเงิน

## 3. บล็อกท้าย — สิ่งที่ทำให้สามใบต่างกัน

### 3.1 ใบเสนอราคา
```
ยืนราคาถึงวันที่ …            ← addWorkingDays(วันที่ออกใบ, 7)                    ← เกินแล้วต้องออกใบใหม่ ไม่ใช่ต่ออายุเงียบ ๆ
เงื่อนไขการชำระเงิน  ฉบับที่ 1.1        ← เลขเวอร์ชันที่ผู้ยื่นกดยอมรับ
[ปุ่มในระบบ]  ยอมรับใบเสนอราคานี้
```
- **ยังไม่มีลายเซ็นผนึก** เพราะยังไม่ใช่หลักฐานทางการเงิน เป็นข้อเสนอ
- เมื่อกดยอมรับ ระบบแช่แข็ง snapshot ของราคา (มี hash) การเปลี่ยนตารางค่าธรรมเนียม
  หลังจากนั้นจะไม่กระทบใบที่รับแล้ว และ checkout ที่ยอดไม่ตรง snapshot จะถูกปฏิเสธ

### 3.2 ใบวางบิล / ใบแจ้งหนี้
```
กำหนดชำระภายในวันที่ …                 ← นับเป็นวันทำการ (utils/working-days)
อ้างอิงใบเสนอราคาเลขที่ …
ช่องทางชำระ: ชำระผ่านระบบ (PromptPay QR)
```
- **ไม่มีเลขบัญชีธนาคารบนใบ** — ช่องทางเดียวคือผ่านระบบ ซึ่ง settlement ยืนยันด้วย webhook
  การพิมพ์เลขบัญชีเปิดช่องให้เกิดการโอนที่ระบบไม่รู้ แล้วต้องมากระทบยอดด้วยมือ

### 3.3 ใบเสร็จรับเงิน / ใบกำกับภาษีเต็มรูป
```
วิธีชำระ: PromptPay QR
อ้างอิงการชำระ: PAY-2569-…
ผู้รับเงิน: ลงนามอิเล็กทรอนิกส์โดยผู้มีอำนาจ
[ลายเซ็นดิจิทัลผนึกไว้]  ตรวจสอบได้ที่ …
                    ↑ เลขที่ใบ TAX-PRD-2569-… เดินต่อเนื่องตาม ม.86/4
                      (กติกาของระบบออกเลข ห้ามข้ามเลข ห้ามออกซ้ำ — ไม่พิมพ์ลงบนใบ)
```
- **ออกได้ต่อเมื่อ webhook ยืนยันการชำระแล้วเท่านั้น** — ใบเสร็จคือคำยืนยันว่าเงินเข้าแล้ว
  ระบบที่ออกใบเสร็จตอน "กดจ่าย" คือระบบที่ออกหลักฐานให้เงินที่ยังไม่มา
- **หนึ่งการชำระ = หนึ่งเลข** ไม่มีการออกใบที่สองสำหรับการจ่ายครั้งเดียว (W14)

**F1-F4 เป็น Tier C** (แตะเส้นเงิน) → operator merge · F5 เป็น docs อย่างเดียว ทำเสร็จแล้ว

> **แก้คำวินิจฉัย 2026-09-05** — ทั้งสี่ข้อเขียนไว้ว่า "ลบเส้นทางของโมเดลเก่า" โดยผมไม่ได้ตรวจว่า
> **ข้อมูลของโมเดลเก่ายังอยู่** · staging ถือใบเสนอราคาฝั่งกรมฯ 16 ใบ และเอกสารทางภาษีที่เปิดไม่ได้
> ไม่ใช่โค้ดที่สะอาดขึ้น มันคือหลักฐานที่หายไป · งานที่ถูกต้องคือ **เขียนเส้นแบ่งเวลา** ให้ของเก่า
> เปิดได้ต่อไปและของใหม่ออกในนามเก่าไม่ได้ — ทำแล้วที่ F1 (`w14-boundary.js`) ส่วน F2 ต้องตรวจ
> ข้อมูลใบเสร็จเก่าด้วยวิธีเดียวกันก่อน และ F4 ตัดสินแล้วว่าไม่ทำ
>
> **สิ่งที่ยังไม่ได้แตะตาม L3**: ยอดเงิน อัตรา และการเคลื่อนเงิน ไม่มีข้อไหนในนี้เปลี่ยนตัวเลข
> ที่ลูกค้าถูกเรียกเก็บ — ด่านนี้ตัดสินแค่ว่า *เอกสารใบไหนเรนเดอร์ในนามผู้ออกรายไหนได้*

## 5. มติ operator 2026-09-05

1. **เลขที่เอกสารแยกชุดตามชนิด** — `QT-PRD-` / `INV-PRD-` / `TAX-PRD-` เดินเลขคนละชุด
   ม.86/4 บังคับความต่อเนื่องเฉพาะใบกำกับภาษี ซึ่งชุด `TAX-PRD-` รับผิดชอบข้อนั้นอยู่แล้ว
   ชุดอื่นจึงไม่ถูกลากเข้าข้อบังคับที่ไม่ได้เขียนถึงมัน และเลขที่บอกชนิดเอกสารได้ในตัว

   **แก้ 2026-09-05 (พบจาก UAT walk)**: ร่างแรกของเอกสารนี้เขียนเลขเป็น `QT-2569-…` คือ **พ.ศ.**
   ซึ่งผิด · `services/document-numbering.js` (ตาม `docs/financial-documents/RECEIPT-DESIGN-SPEC.md §5`)
   แยกไว้ชัดเจนแล้วและถูกต้อง:

   | ผู้ออก | ปีที่ใช้ | เหตุผล |
   |---|---|---|
   | กรมฯ (`RCP-DTAM-`) | **พ.ศ.** | ธรรมเนียมราชการ |
   | บริษัท (`*-PRD-`) | **ค.ศ.** | ข้อกำหนดการยื่นของสรรพากร |

   W14 เหลือผู้ออกรายเดียวคือ**บริษัท** ⇒ ทั้งสามใบเป็นเอกสารฝั่ง PRD ⇒ **ใช้ ค.ศ. ทั้งหมด**
   ยืนยันจากของจริง: คำขอที่ยื่นใน UAT walk ได้ `QT-PRD-2026-000001` ขณะที่เลขคำขอเป็น
   `APP-2569-…` — สองระบบปีในวันเดียวกัน และทั้งคู่ถูกต้องตามธรรมเนียมของตัวเอง
2. **ใบวางบิลกับใบแจ้งหนี้เป็นใบเดียวกัน** — เอกสารทั้งชุดจึงมีสามใบ ไม่ใช่สี่ใบ
   ใบที่สองพิมพ์หัวว่า "ใบวางบิล / ใบแจ้งหนี้" ใช้ชุดเลข `INV-` ชุดเดียว
   ไม่มีเอกสารชนิดที่สี่ ไม่มีเลขชุดที่สี่ และลูกค้าองค์กรที่ขอ "ใบวางบิล" ได้ใบนี้

3. **ยืนราคา 7 วันทำการ** นับจากวันที่ออกใบ ด้วย `utils/working-days.js` ตัวเดียวกับที่กำหนดชำระใช้

   **กฎหมายไม่ได้กำหนดจำนวนวันไว้** ใบเสนอราคาคือ *คำเสนอ* ตาม ป.พ.พ.:
   - **ม.354** คำเสนอที่ *ระบุ* เวลาให้ทำคำสนอง ถอนไม่ได้ภายในเวลานั้น → เขียน 7 วันลงไป
     บริษัทผูกพันราคาไว้ 7 วันจริง และผูกพันเพียงเท่านั้น
   - **ม.355** คำเสนอที่ *ไม่ระบุ* เวลา สิ้นผลเมื่อพ้น "เวลาอันควรคาดหมายว่าจะได้รับคำบอกกล่าวสนอง"
     — ปล่อยว่างคือปล่อยให้ตีความทีหลัง ซึ่งแย่กว่าตัวเลขที่สั้นไปเล็กน้อย
   - **ม.357** คำสนองที่มาช้ากว่ากำหนด ไม่เกิดผล → ใบที่หมดอายุต้องออกใหม่ ไม่ใช่ต่ออายุเงียบ ๆ

   (พ.ร.บ.จัดซื้อจัดจ้างฯ 2560 ที่บังคับระยะยืนราคา ใช้กับกรณี *รัฐเป็นผู้ซื้อ* — ที่นี่บริษัทเป็นผู้ขาย
   เกษตรกรเป็นผู้ซื้อ จึงไม่เข้าเงื่อนไขนั้น)

   **ทำไมนับวันทำการ ไม่ใช่วันปฏิทิน** — เหตุผลเดียวกับกำหนดชำระบนใบแจ้งหนี้ ซึ่งนับวันทำการอยู่แล้ว:
   ใบที่ออกวันศุกร์ก่อนสงกรานต์ ถ้านับปฏิทินจะเหลือเวลาจริงให้เกษตรกรหาเงินราวสองวัน
   ระบบมีปฏิทินตัวนี้อยู่แล้ว จึงไม่ใช่ความซับซ้อนใหม่ · **พิมพ์เป็นวันที่จริง ไม่ใช่ข้อความ "7 วัน"**
