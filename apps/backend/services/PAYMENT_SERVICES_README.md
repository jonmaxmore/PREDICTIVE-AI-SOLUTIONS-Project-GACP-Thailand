# Payment Services — Architecture Guide

> **สำหรับคนที่เพิ่งเข้ามาอ่าน**: ไฟล์นี้เคยบอกตรงกันข้ามกับความจริงทั้งหน้า
> (เขียนไว้ว่า flow หลักคือ "อัปโหลดสลิปแล้วเจ้าหน้าที่ตรวจ" และ webhook คือของเลิกใช้)
> เขียนใหม่ทั้งฉบับ 2026-09-11 · ทุกไฟล์ที่ฉบับเดิมเรียกว่า "canonical" หรือ
> "deprecated" ถูกลบออกจาก tree ไปแล้ว — เอกสารที่ชี้ไปยังไฟล์ที่ไม่มี
> อันตรายกว่าไม่มีเอกสาร เพราะคนอ่านจะไปสร้างของต่อบนสิ่งที่ไม่มีอยู่

## เส้นทางจริงของเงิน (Stripe checkout · settle ด้วย webhook)

```
1. ผู้ยื่นส่งคำขอ (DRAFT → SUBMITTED → PENDING_DOC_FEE)
   → ระบบออกใบเสนอราคาให้เอง (services/quotation-issuance-on-submit.js)

2. ผู้ยื่นกดชำระ → Stripe Checkout
   → services/checkout/stripe-checkout-service.js

3. Stripe ยิงกลับมาที่ routes/api/webhooks/stripe.js
   → ยืนยันลายเซ็นบน raw bytes ก่อนทุกอย่าง (ไม่มี auth middleware:
     ความถูกต้องคือลายเซ็น · ไม่มี STRIPE_WEBHOOK_SECRET = ประตูไม่ติดตั้งเลย)
   → services/checkout/checkout-settlement-service.js
        M1 → DOC_FEE_PAID    (งวดที่ 1 ค่าบริการตรวจสอบเอกสาร)
        M2 → AUDIT_FEE_PAID  (งวดที่ 2 ค่าบริการตรวจประเมินแปลงและออกใบรับรอง)
   → ลงบัญชี recordPaymentEntry (journal-entry-service) ในทรานแซกชันเดียวกัน
   → ออกใบเสร็จ

4. เอกสารผ่าน (DOC_APPROVED → PENDING_AUDIT_FEE)
   → ระบบออกใบของงวดที่ 2 ให้เองทันที (F-G4-71, operator 2026-09-06 —
     routes/api/provider/handlers/workflow-side-effects.js)

5. งวดที่ 2 ชำระแล้ว (AUDIT_FEE_PAID) → ผู้จัดสรรงานนัดวัน → AUDIT_CONFIRMED
```

**ไม่มีมนุษย์คนใดอนุมัติการชำระเงิน** — ไม่มีขาในตารางเปลี่ยนสถานะให้บทบาทการเงิน
เดินเลย (`workflow-transition-service.js` — สองบทบาทนั้นถือชุดว่างโดยตั้งใจ)

## ไฟล์ที่ยังอยู่ และหน้าที่ของมัน

| ไฟล์ | หน้าที่ |
|------|--------|
| `checkout/stripe-checkout-service.js` | สร้าง checkout session และใบแจ้งหนี้ของรอบนั้น |
| `checkout/checkout-settlement-service.js` | **จุดเดียวที่เปลี่ยนสถานะเป็นชำระแล้ว** — idempotent ต่อ event |
| `quotation-issuance-on-submit.js` | ออกใบเสนอราคาตอนยื่น ตอนต่ออายุ และตอนเอกสารผ่าน |
| `payment/stripe-adapter.js` · `payment/payment-adapter.js` | ซีมของผู้ให้บริการชำระเงิน — เปลี่ยนเจ้าได้โดยไม่แตะ settlement |
| `payment-service.js` · `payment-service-phase-flow.js` | ออกใบแจ้งหนี้ต่องวด (ไม่เปลี่ยนสถานะเป็นชำระแล้ว) |
| `split-payment-calculator.js` | แยกส่วนรัฐ / ส่วนแพลตฟอร์ม + VAT |
| `journal-entry-service.js` | ลงบัญชี · Dr เงินสด / Cr รายได้ค่าบริการ / Cr ภาษีขาย — ไม่มีบรรทัดของกรมฯ (ดูหัวข้อล่างสุด) |
| `../modules/billing/internal/fee-service.js` | ตัวคิดค่าธรรมเนียม — **แหล่งเดียวของตัวเลข** |

## ค่าธรรมเนียม: อย่าพิมพ์ตัวเลขลงเอกสารหรือคอมเมนต์

ฉบับเดิมเขียนว่างวดที่ 1 = 5,535 และงวดที่ 2 = 27,675 · ทั้งคู่เป็น **สูตรที่เลิกใช้**
(VAT เคยคิดเฉพาะค่าบริการแพลตฟอร์ม) ตัวเลขจริงต่อหนึ่งลักษณะพื้นที่ วัดจาก
`fee-service` วันที่เขียน: **5,885 / 29,425 รวม 35,310** และค่าบริการเป็น
**ผลบวกต่อจำนวนลักษณะพื้นที่ที่ประกาศ** (operator 2026-09-06)

ถามตัวคิดเงินเสมอ อย่าพิมพ์ตัวเลขซ้ำ — ตัวเลขที่พิมพ์ไว้ในคอมเมนต์ไม่มีด่านใดคอยแก้
ตอนอัตราเปลี่ยน และมันเคยพาให้ตัดสินใจผิดมาแล้วจริง

## กรมฯ ไม่อยู่ในสมุดบัญชีของแพลตฟอร์ม (operator 2026-09-29)

บริษัทชำระกับกรมการแพทย์แผนไทยฯ **นอกระบบ** และลงบัญชีในสมุดบัญชีของบริษัทเอง ·
แพลตฟอร์มไม่มีเจ้าหนี้กรมฯ (2151-001) ไม่มีต้นทุนค่าธรรมเนียมกรมฯ (5110-001) ไม่มี pipeline
นำส่ง และไม่แยกส่วนค่าธรรมเนียมของกรมฯ ในราคา · รายการบัญชีตอนชำระเงินมีสามบรรทัดเท่านั้น:
เงินสด (1110-001) / รายได้ค่าบริการ (4110-001) / ภาษีขาย 7% (2131-001)

ประวัติ: หัวข้อนี้เคยอธิบายโมเดล "ตัวแทนรับชำระ" (2026-05-16) ที่เครดิต `PAYABLE_TO_DTAM`
และล้างด้วย `recordRemittanceToDtam()` — ถูกแทนด้วย W14 (ผู้ขายรายเดียว 2026-08-22),
ค่าบริการก้อนเดียว (2026-09-11) และมติ 2026-09-29 ตามลำดับ · ทั้งสองชื่อไม่มีในโค้ดแล้ว
(กันด้วย `__tests__/unit/dtam-accounting-layer-removed.test.js`)
